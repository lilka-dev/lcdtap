# 0015: Lilka LCD-TAP アダプタで 74HC595 のラッチがバイト途中で競合する

## 現象

Lilka v2 (ESP32-S3) の LCD SPI を 007_LCD-TAP アダプタ (74VHC4040 + 74HC595) で
8bit パラレルに変換して pico2_universal (Parallel8) に入力すると、ストローブ数は
1 バイトにつき 1 回で D/C も正しいが、データ値が化ける。

Lilka にテストファームを書き込み、既知のバイト列を送って Command Dump で比較した
結果 (SPI 1/10/80 MHz で同一、40 MHz で一部ビットが揺らぐ):

| 送信 (同一値の繰り返し) | 受信 |
|---|---|
| 0x00 / 0xFF | 0x00 / 0xFF |
| 0x01 | 0x18 |
| 0x0F | 0xF8 |
| 0xF0 | 0x8F |
| 0x33 | 0xBB |
| 0x80 | 0x0C (単発の 0x80 では 0x04) |

ランプ (0x00, 0x01, ...) を含め、受信値は次の式に一致する:

```
capture[i] = ((b[i-1] << 4) | (b[i] >> 4)) | ((b[i-1] << 3) | (b[i] >> 5))   (8bit)
```

## 原因

修正後の配線 (SCK → インバータ → 4040 /CK、4040 Q3 → LCD_WR = 595 STCP) では
4040 は SCK 立ち上がりでカウントし、Q3 (÷8) の立ち上がりは **各バイトの 4 クロック目**
になる。595 の SHCP も同じ SCK 立ち上がりなので:

1. ラッチ位置がバイト境界から 4 ビットずれる (前バイト下位ニブル + 現バイト上位ニブル)。
2. STCP (インバータ + リップル遅延のみ) が SHCP とほぼ同時に立ち上がるため、
   ストレージレジスタがシフト中の値を取り込み、シフト前後の窓の OR に近い値になる
   (データ依存・速度非依存)。

2 は情報が失われるため、ソフトウェアでは復元できない。

参考: rev01 回路 (SCK → 4040 CK 直結、Q3 → インバータ → WR) は SCK 立ち下がり
8 回目 + リップル遅延でラッチするため、低速では整列し、80 MHz ではリップル遅延
(~15–20 ns) が半周期 (6.25 ns) を超えて 1 ビットずれる。以前の `bitOffsetFix`
(1 ビット補正) はこの状態に対するもので、クロック依存のため削除した。

## 対策 (ハードウェア)

- ラッチは「8 回目の SHCP の後、9 回目の SHCP の前」に来る必要がある。80 MHz では
  窓が 12.5 ns しかなく、リップルカウンタ (4040) と 74HC595 (3.3 V での fmax 保証外)
  では満たせない。
- 推奨: 同期カウンタ (74LVC161/163 など) を SCK 立ち上がりで動かし、/QC (÷8 の
  反転) を STCP/WR にする。595 は 74LVC595A / 74AHC595 に置き換える。
- 代替: Lilka 側の表示 SPI クロックを下げ (Keira は `Arduino_ST7789::begin(80000000)`)、
  rev01 配線で整列する速度を実測で確認する。pico2_universal の入力スループット
  上限 (62.5 MHz SPI 相当) からも 80 MHz は超過している。

## Lilka プリセット

Keira は 240x280 パネルを Arduino_GFX rotation 3 (MADCTL MY|MV) + 20 ライン
オフセットで描画するため、画像は GRAM 240x320 の行 20..299 に入る。プリセットを
280x240 から 240x320 + CUSTOM トリム (0, 20, 240, 280) + outputRotation 1 に修正し、
`verify_test` の `testLilkaKeiraAddressing` で正立出力を確認した。

## 再現手順

Lilka テストファーム (SPI の CS/DC/データを行単位で送出) と Command Dump を使い、
`r64:0F` (0x0F を 64 バイト) 等を送って受信値を比較する。
